# Spec: Registration

## Overview
Turn the static sign-up page into a working registration flow. `GET /register`
already renders `register.html`, but the form posts to a route that does not
accept POST, so no user can be created. This step adds POST handling: validate
the submitted name, email and password, hash the password with werkzeug, insert
the user into the `users` table, and redirect to the login page with a success
message. It is the first user-facing feature built on the Step 1 data layer and
is a prerequisite for login/logout (Step 3) and every logged-in page after it.

## Depends on
- **Step 1 — Database setup**: `get_db()`, `init_db()` and the `users` table
  (`id`, `name`, `email UNIQUE`, `password_hash`, `created_at`) in
  `database/db.py`.

## Routes
- `GET /register` — render the empty registration form — public (already exists; keep it)
- `POST /register` — validate input, create the user, flash a success message
  and redirect to `login` on success; on failure re-render `register.html`
  with an `error` message and the previously entered name/email — public

Implement both on the existing `register()` view using
`methods=["GET", "POST"]`. Do not add a separate endpoint.

## Database changes
No database changes. The existing `users` table already has every column and
the `UNIQUE` constraint on `email` that registration needs.

New helper functions in `database/db.py` (no schema changes):
- `get_user_by_email(email)` — return the matching `sqlite3.Row` or `None`
- `create_user(name, email, password)` — hash the password with
  `generate_password_hash`, insert the row with a parameterised query, commit,
  and return the new user's id. Let `sqlite3.IntegrityError` propagate (or
  return `None`) on a duplicate email so the route can show a friendly error.
  Always close the connection in a `finally` block, matching `seed_db()`.

## Templates
- **Create:** none
- **Modify:**
  - `templates/register.html`
    - Change `action="/register"` to `action="{{ url_for('register') }}"`
    - Repopulate `name` and `email` inputs from values passed by the route
      after a failed submission (never repopulate the password)
    - Add `minlength="8"` to the password input
  - `templates/login.html`
    - Render flashed messages (`get_flashed_messages(with_categories=true)`)
      so "Account created — please sign in" appears after registration

## Rules for implementation
- No SQLAlchemy or ORMs
- Parameterised queries only (`?` placeholders), never f-strings in SQL
- Passwords hashed with werkzeug (`generate_password_hash`); never store or log
  the plain password
- Use CSS variables — never hardcode hex values
- All templates extend `base.html`
- All DB access lives in `database/db.py`; the route only validates, calls the
  helpers, and renders or redirects
- Use `url_for()` for every internal link and redirect; never hardcode URLs
- Validation, server-side, in this order, re-rendering with one clear `error`:
  - name, email and password are all required (after `.strip()`)
  - email must contain `@` and a `.` after it (basic check, no new packages)
  - password must be at least 8 characters
  - email must not already be registered (check is case-insensitive: store
    and compare emails lowercased)
- Return HTTP 400 status when re-rendering the form for a validation error
- Do not log the user in automatically. Session login belongs to Step 3
- Do not implement any stub routes (`/logout`, `/profile`, `/expenses/...`)
- Keep the dev server on port 5001

## Definition of done
- [ ] `python app.py` starts on port 5001 with no errors
- [ ] `GET /register` shows the form and its `action` is generated by `url_for`
- [ ] Submitting a valid name, email and an 8+ character password creates a
      row in `users` and redirects to `/login`
- [ ] The login page then shows a green "Account created — please sign in" message
- [ ] The stored `password_hash` is a werkzeug hash, not the plain password
- [ ] Registering `demo@spendly.com` (or `DEMO@spendly.com`) shows
      "An account with that email already exists" and creates no new row
- [ ] Submitting a blank name, a blank or malformed email, or a password under
      8 characters re-renders the form with an error and a 400 status
- [ ] After a failed submission the name and email fields keep their values;
      the password field is empty
- [ ] No hex colour values are added to any CSS file
- [ ] `pytest` passes, including the new tests in `tests/test_registration.py`
      that cover success, duplicate email, and each validation error
